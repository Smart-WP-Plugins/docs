Following a preset link always ends in a redirect. Where to depends on one thing: whether anything reached the cart.

If something did, the link worked — whole or in part — and **Redirect after adding** decides. If nothing did, the link was refused, and **Unavailable links** decides. Both live under **Settings → Cart behaviour**, and a preset can answer either for itself.

## Redirect after adding

Set store-wide under **Settings → Cart behaviour → Redirect after adding**, and overridable per preset.

| Choice | Where they go | Key |
| --- | --- | --- |
| Cart | Your cart page, holding the preset | `cart` |
| Checkout | Straight to checkout | `checkout` |
| Stay on the page | Back where they came from | `stay` |
| Custom URL | An address you choose, in the **Custom URL** field below the choices | `custom` |

The same four choices, in the same words, appear store-wide and on a single preset.

**Cart** is the default and the safe choice: the customer sees what they got before they commit to it.

**Checkout** shortens the path for a campaign where the offer is already understood.

**Stay on the page** is for links embedded in your own content. A button inside a blog post can fill the cart and leave the reader exactly where they were reading.

<Media>The "Redirect after adding" block with the four choices, Custom URL selected and an address entered</Media>

### How "stay" decides where that is

From the referring page, and only if it is one of yours.

A referer from another site is ignored and the customer goes to your home page instead. Otherwise any site could embed your preset link and bounce your customers back to themselves.

No referer at all — a link pasted into the address bar, or a browser that sends none — also goes to your home page.

### Per-preset override

Each preset can choose its own destination in the editor's **Cart behaviour** card, under **Redirect after adding**, or leave it on **Use the Settings default**. That row names the store's current choice, so you can see what following the default means without leaving the page.

## Unavailable links

A link can be refused nine ways, and they all share one answer.

They used to travel two paths that disagreed: three were configurable and left the customer on the cart, six were hard-coded to a fallback URL nobody could set per preset. A merchant could redirect a sold-out preset and not an ineligible one, for no reason they could have predicted.

| Setting | Choices | Key |
| --- | --- | --- |
| Send them to | **Cart** · **Custom URL** | `refused_action` |
| Custom URL | Required when a custom link is chosen | `refused_url` |
| Show an error message | On by default | `refused_notice` |

Each reason keeps its own sentence — "sold out" is not "please sign in". What is shared is where the customer goes and whether they are told anything at all.

| Situation | Notice ID |
| --- | --- |
| The link matches no preset | `not_found` |
| Not started yet<Pro /> | `scheduled` |
| Ended, inactive, or sold out | `unavailable` |
| Not enough room left under the total cap<Pro /> | `limit_total` |
| Per-customer cap reached<Pro /> | `limit_customer` |
| The preset is for signed-in customers only<Pro /> | `not_signed_in` |
| The customer holds none of the roles the preset allows<Pro /> | `role_not_allowed` |
| The preset has no items | `no_items` |
| An item cannot be bought, and your rule is "refuse the preset" | `item_blocked` |
| Every item failed at cart time | `nothing_added` |

All ten sentences are yours to rewrite — see [Cart notices and wording](/cartpresets/links/wording).

<Note>
  **The store's Fallback link is gone**, and the chain behind it — fallback link, then shop page, then home. Two ways to answer one question was the confusion. A merchant who wants refused customers on the shop page pastes the shop page as the custom URL, and can see that they did.
</Note>

### Telling them why

The reason is shown as a WooCommerce notice, which the **theme** prints rather than this plugin.

The cart always prints them, and so do the Cart and Checkout blocks. A custom landing page often does not: a page template that never calls `woocommerce_output_all_notices` shows nothing, however the switch is set. Worth testing the page you chose before a campaign goes out.

### Per-preset override

A preset carries the same three keys, where `refused_action` also accepts `global` to follow the store. It is set in the editor's **Cart behaviour** card, under **Unavailable links**, and is Pro to edit — a stored answer is still honoured on the free version.

A custom destination with no address resolves to the cart. Both screens refuse to save an empty one, so that is a floor under corrupted data rather than something you can configure.

## A refusal is not a partial success

Sometimes most of a preset works. That is a **success**, and none of the settings above about refusals apply to it: the customer keeps what could be added, **Redirect after adding** decides where they land, an automatic coupon still applies, and the caveat message explains what was skipped.

| Situation | Notice ID |
| --- | --- |
| They already hold this preset | `already_in_cart` |
| One item is out of stock | `item_out_of_stock` |
| One item is limited to one per order, so the quantity was trimmed | `item_qty_capped` |
| One item is unavailable for any other reason | `item_unavailable` |

Whether a failing item is skipped or refuses the whole preset is the **Unavailable items** setting — see [Items](/cartpresets/building/items). Choosing "Refuse the preset" turns that case into a refusal, `item_blocked`, and nothing reaches the cart.

## External addresses work

Custom destinations, per-preset custom URLs and refusal links may all point at another domain.

WordPress's own `wp_safe_redirect()` would silently rewrite a foreign host to wp-admin — sending your customer to a dashboard login. CartPresets passes merchant-configured destinations through a helper that allow-lists the host you actually configured, so the address you typed is the address they reach.

<Note>
  This applies only to addresses **you** configured in settings. A host arriving in a request is never trusted.
</Note>

## Settings reference

| Setting | Level | Key | Default |
| --- | --- | --- | --- |
| Redirect after adding | Store | `post_add` | `cart` |
| Custom URL | Store | `post_add_url` | Empty |
| Destination | Preset | `redirect` | `global` |
| Custom URL | Preset | `custom_url` | Empty |
| Unavailable links | Store | `refused_action` | `cart` |
| Custom URL | Store | `refused_url` | Empty |
| Show an error message | Store | `refused_notice` | On |
| Unavailable links | Preset | `refused_action` | `global` |
| Custom URL | Preset | `refused_url` | Empty |
| Show an error message | Preset | `refused_notice` | On |

## For developers

`cartpresets_post_add_url` filters the resolved destination and is safety-clamped. See the [hooks reference](/cartpresets/developers/hooks-reference#cart).
