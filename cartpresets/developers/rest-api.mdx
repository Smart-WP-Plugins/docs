Every route CartPresets for WooCommerce registers lives under one namespace: **`cartpresets/v1`**.

<Warning>
  **There are no public endpoints.** Every route requires the `manage_woocommerce` capability and a valid nonce. They exist to serve the admin panel, not to be a storefront API. A preset reaches a customer through its link, not through REST.
</Warning>

The capability is filterable through `cartpresets_admin_capability`, which is safety-clamped.

## Presets

| Method | Route | Does |
| --- | --- | --- |
| `GET` | `/presets` | List, with search, filters, sort and pagination |
| `POST` | `/presets` | Create |
| `GET` | `/presets/<id>` | Read one |
| `PUT` | `/presets/<id>` | Update |
| `DELETE` | `/presets/<id>` | Delete |
| `POST` | `/presets/<id>/duplicate` | Copy, inactive |
| `POST` | `/presets/bulk` | Act on several at once |
| `GET` | `/presets/slug-check` | Whether a slug is available |
| `GET` | `/presets/export`<Pro /> | Export as JSON |
| `POST` | `/presets/import`<Pro /> | Import from JSON |

### Listing parameters

`GET /presets` accepts `search`, `status`, `sort`, `dir`, `page`, `per_page` (up to 200) and `filters`, plus the pre-builder arguments `added_after`, `added_before`, `price_op`, `price`, `price_max`, `orders_op`, `orders`, `orders_max`, `product`, `stock_problem` and `has_coupon`.

- `search` also looks inside a preset: product and variation names, SKUs, and custom item names.
- `sort` takes `name`, `status`, `items`, `price`, `revenue`, `orders` or `publish`, with `dir` as `asc` or `desc`.
- `filters` takes the fields `price`, `revenue`, `items`, `orders`, `date` and `product`, among others.

[`cartpresets_list_args`](/cartpresets/developers/hooks-reference#listing) documents the full grammar. It receives exactly these arguments once they're resolved.

A `revenue` sort or filter is Pro. On the free version the route refuses it with a 400 (`cartpresets_needs_pro`) instead of treating every preset as unsold.

```bash
curl -s 'https://yourstore.com/wp-json/cartpresets/v1/presets?status=active&sort=price&dir=asc&per_page=5' \
  -H 'X-WP-Nonce: <nonce>' \
  --cookie 'wordpress_logged_in_...=<cookie>'
```

The answer is `presets`, `total` and `counts`. `counts` holds one number per derived status, plus `all`, and it's always the whole store's: no search, filter or status narrows it.

### What a preset carries

Among the rest, each preset in the answer has:

| Key | Holds |
| --- | --- |
| `derived_status` | `active`, `scheduled`, `expired`, `sold_out` or `inactive` |
| `warnings` | Cautions about the items, as `{ label, kind }`: `unpublished`, `out_of_stock`, `low_stock`, or `open_quantity` (a capped preset whose quantity has no upper limit) |
| `attention` | Items with a problem that won't fix itself, as `{ item_id, product_id, label, kind }`. `kind` is `unpublished` (with the product's `status`), `missing` (deleted, or never chosen) or `not_purchasable` (a variable product with no variation chosen, a grouped or external product, or one with no price) |
| `needs_attention` | `true` when the preset is `active` and `attention` isn't empty. It's what the listing's **Needs attention** badge reads. It isn't a status, so it has no tab or count |
| `totals` | The preset's price before and after its discounts |
| `items` | Each with `purchasable`. On `GET /presets/<id>`, each also carries `product_type` and `subscription` (see [Products](#supporting-routes)) |

### Saving

`PUT /presets/<id>` replaces the preset. `created_at`, the publish date, is Pro to change: sent empty, it's saved as the moment of the save, and left out, it keeps the stored date. On the free version the stored date is kept either way.

### Bulk actions

`POST /presets/bulk` takes an `action`: `activate`, `deactivate`, `duplicate`, `clear_end_date` or `delete`. It names the presets one of two ways:

- **`ids`**: the presets you ticked.
- **`query`**: `{ search, status, filters }`, validated the way the listing validates them, for every preset that matches. This is the listing's **select all** across pages. Send `expect` with it: the count the merchant confirmed. If the query matches a different number by the time it runs, nothing changes and the answer is a 409 (`cartpresets_bulk_changed`) with the new count in `data.total`.

One request acts on at most **500** presets. More is refused whole, with a 400.

The answer is `{ action, affected, matched }`, plus `created` (the new IDs) for `duplicate`. Copies are inactive. `clear_end_date` asks the same tier gate a save asks, so it's Pro.

### Export and import<Pro />

`GET /presets/export` exports `ids[]` when given. Otherwise it exports every preset matching `search`, `status` and `filters`, and with none of those, every preset. There's no ceiling.

`POST /presets/import` takes an export document and creates presets from it, inactive. One import takes up to 500 presets; the rest are reported as skipped. See [Import and export](/cartpresets/import-export).

## Settings

| Method | Route | Does |
| --- | --- | --- |
| `GET` | `/settings` | Read all store settings |
| `POST` | `/settings` | Save them |
| `POST` | `/settings/carrier` | Create, choose or unlink the carrier product |
| `GET` | `/settings/carrier-options` | Products that could be the carrier |

`GET /settings` answers `settings`, `carrier` and `samples`. `carrier` is `null`, or `{ id, name, edit, virtual, hidden }`. `virtual` and `hidden` are read from the product itself; `hidden` means its catalogue visibility is hidden.

`GET /settings/carrier-options` takes an optional `search` (a name, or an exact product ID). It answers `products`: up to thirty published, virtual, simple products, newest first, each `{ id, name, virtual, hidden, current }`. `current` marks the carrier now. Choosing a product that isn't virtual is refused.

## Supporting routes

| Method | Route | Does |
| --- | --- | --- |
| `GET` | `/products` | The editor's product picker |
| `GET` | `/reference` | Shipping classes, roles, the store's weight and dimension units, and the system status report |
| `GET` | `/prefs` | The current user's listing preferences |
| `POST` | `/prefs` | Save them |

`GET /products` answers twelve suggestions with no `search`, and up to thirty matches with one. A search matches a name, a SKU, or a variation's name or SKU. Each product carries:

- `type`: WooCommerce's own, such as `simple`, `variable`, `subscription` or `variable-subscription`.
- `subscription`: `null` unless the product bills as a subscription, otherwise `{ period, interval, length, trial_period, trial_length, sign_up_fee }`. A variable subscription's `variations` each carry their own.

`POST /prefs` saves any of `fields` (the optional columns), `per_page` (10, 20 or 50), `sort` (a listing sort key) and `dir` (`asc` or `desc`). A key you leave out keeps its stored value. `GET /prefs` answers `{}` until the first save.

| Method | Route | Does |
| --- | --- | --- |
| `GET` | `/sales` | Rows and the orders drill-down |
| `GET` | `/sales/stats` | Totals and the time series |
| `GET` | `/sales/presets` | Preset names, for the report's filters |

## Licensing<Pro />

| Method | Route | Does |
| --- | --- | --- |
| `GET` | `/licence` | Current state — never the key itself |
| `POST` | `/licence` | Activate |
| `DELETE` | `/licence` | Deactivate |
| `POST` | `/licence/sync` | Re-check now |

`POST /licence` takes `key`. If the key has no account attached yet, the answer is a 409 (`cartpresets_licence_identity_required`) carrying the `name` and `email` that activating would send. Nothing is sent until you call again with `confirm_identity: true`. The Licence card asks the merchant first. See [Licence and updates](/cartpresets/licence#activating).

<Note>
  A licence key travels **in** and never back out. `GET /licence` returns the status, plan, expiry, sites in use and when it was last checked, plus a masked copy showing only the key's last four characters.
</Note>

## Absent, not refusing

On the free version the Pro routes are **not registered at all**. A request to `/sales` or `/presets/import` returns a plain 404, exactly like a route that never existed.

That's deliberate. A route that exists and refuses tells an attacker the feature is there; a route that doesn't exist tells them nothing. It also means the free version ships no premium code to refuse with.

```php
if ( ! \SmartWP\CartPresets\Support\Tier::is_pro() ) {
	// Do not call /sales here — it will 404.
}
```

## Adding your own routes

Register on `cartpresets_register_rest_routes`, which fires once the plugin's own controllers are up. Pro uses the same seam, so nothing about the premium routes is privileged.

```php
add_action( 'cartpresets_register_rest_routes', function () {
	register_rest_route( 'cartpresets/v1', '/my-thing', array(
		'methods'             => 'GET',
		'callback'            => 'my_plugin_handler',
		'permission_callback' => function () {
			return current_user_can( 'manage_woocommerce' );
		},
	) );
} );
```

<Warning>
  Supply your own `permission_callback`. Registering inside this action doesn't inherit the plugin's capability check.
</Warning>
