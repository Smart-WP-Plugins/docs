Settings live at three levels. A preset-level setting overrides the store-wide one; an item-level setting applies to one line.

All store settings live in a single option, `cartpresets_settings`. Preset and item settings live in their own tables.

## Store settings

### Licence<Pro />

On Pro the first card on Settings is **Licence**, above the carrier product. It holds the key, its status, and the Activate, Sync and Deactivate buttons. Those buttons act immediately and sit outside the save bar, so there is nothing to save. The licence has no stored setting keys in `cartpresets_settings`. See [Licence and updates](/cartpresets/licence).

### Carrier product

| Setting | Key | Default | Tier |
| --- | --- | --- | --- |
| Carrier product | `carrier_product_id` | `0` (none) | Both |

The hidden product custom items ride on. See [The carrier product](/cartpresets/settings/carrier-product).

### Cart behaviour

| Setting | Key | Default | Tier |
| --- | --- | --- | --- |
| Clear the existing cart | `clear_cart` | Off | Both |
| Allow the same preset twice | `allow_duplicate` | Off | Both |
| Keep the customer's own items | `keep_existing` | On | Both |
| If an item cannot be added | `invalid_item` | `skip` | Both |
| Order statuses that use up a purchase limit | `redemption_statuses` | on-hold, processing, completed | Pro to edit, honoured on both |
| After a successful add | `post_add` | `cart` | Both |
| Custom URL | `post_add_url` | Empty | Both |

`invalid_item` accepts `skip` (**Skip the item**) or `none` (**Refuse the whole preset**). `post_add` accepts `cart`, `checkout`, `stay` or `custom`.

### Cart notices and labels

| --- | --- | --- | --- |

### Links and fallbacks

### Admin menu

| Setting | Key | Default | Tier |
| --- | --- | --- | --- |
| Where you reach this panel from | `menu_location` | `own` | Both |

`own` is a top-level **Cart Presets** menu with All Presets, Add New Preset and Settings beneath it. `products` is a single **Cart Presets** entry under **Products**, with no submenu; Add New and Settings stay reachable from the listing screen. Saving this reloads the page to move the menu.

## Preset settings

Set in the editor, on one preset.

| Setting | Key | Default | Tier |
| --- | --- | --- | --- |
| Date (publish) | `created_at` | Now | Pro to edit |
| Ends | `end_at` | Empty | Pro to edit |
| Maximum purchases | `max_total` | Empty | Pro to edit, honoured on both |
| Maximum per customer | `max_per` | `0` | Pro to edit, honoured on both |
| Destination after add | `redirect` | `global` | Both |
| Custom URL | `custom_url` | Empty | Both |
| Use the Settings default (the cart this link finds) | `cart_override` | Off (follow Settings) | Both |
| Clear the existing cart | `clear_cart` | Off | Both |
| Allow the same preset twice | `allow_duplicate` | Off | Both |
| Keep the customer's own items | `keep_existing` | On | Both |
| Coupon code | `coupon` | Empty | Pro — not applied on free |
| Signed-in customers only | `logged_in` | Off | Pro |
| Allowed roles | `roles` | Empty | Pro |
| Rejection message | `reject_message` | Empty | Pro |
| When this preset reaches its limit or its end date | `unavailable_action` | `global` | Pro to edit |
| Redirect to | `unavailable_url` | Empty (falls through to the fallback link) | Pro to edit |
| Show a notice that it is unavailable | `unavailable_notice` | On | Pro to edit |

`redirect` and `unavailable_action` accept `global` (**Use the Settings default**); `unavailable_action` otherwise accepts `notice` or `redirect`.

The three cart switches are read only while `cart_override` is on. With it off the store's own answers apply, and the editor draws them disabled — see [Cart behaviour](/cartpresets/links/cart-behaviour#per-preset-override).

## What "Pro to edit, honoured on both" means

Some settings can only be *set* on Pro, but are *enforced* in both versions.

Purchase limits are the clearest case. Setting a cap needs Pro. Counting claims against one, and refusing a link once it fills, happens on both — because moving to the free version must never put a sold-out link back on sale.

The same logic covers schedules. The general rule: **honour the restriction, drop the enhancement.**

## Where settings are stored

| Level | Storage |
| --- | --- |
| Store | One option, `cartpresets_settings` |
| Preset | Columns and a settings blob on `cartpresets_presets` |
| Item | A settings blob on `cartpresets_items` |

Writes walk the schema rather than the request, so a key that is not in the schema is never persisted no matter what a request contains. Developers can register their own keys — see [the hooks reference](/cartpresets/developers/hooks-reference#schema).
