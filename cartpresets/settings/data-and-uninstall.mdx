## What is stored

Four tables and one option:

| Table | Holds | Personal data |
| --- | --- | --- |
| `cartpresets_presets` | Presets — name, slug, status, dates, caps, settings | None |
| `cartpresets_items` | The items inside each preset | None |
| `cartpresets_redemptions` | One row per claim, for purchase limits | The order ID, and a user ID or a guest's billing email |
| `cartpresets_slug_history` | Old slugs, for 30-day redirects | None |

Plus the `cartpresets_settings` option, and meta on order line items — see [Order line item meta](/cartpresets/developers/order-meta).

### The one row with personal data in it

A redemption records who claimed a preset, so a per-customer cap can be enforced. For a signed-in customer that's their user ID. For a guest it's their billing email address, lowercased — the only stable way to recognise the same guest twice. No IP address is recorded. A developer can change how customers are identified with `cartpresets_redemption_customer_key`.

Without it there can be no per-customer limit. You can't know somebody has already claimed something if you don't record that they did.

A customer can ask for that record, and ask for it to be forgotten: see [Privacy and personal data](/cartpresets/settings/privacy).

## What leaves your site

**Nothing, on the free version.** No analytics, no phone-home, no scripts or styles enqueued on your storefront at all.

**On CartPresets for WooCommerce Pro**, one thing: a licence check. Your licence key and site URL go to the licensing service to activate, to verify periodically, and to check for updates. It runs from wp-admin and cron only, never from your storefront, so a customer browsing your shop never triggers it.

The Presets report reads your own WooCommerce order tables. Those figures never leave your site.

<Note>
  The **Copy system report** button on the Settings sidebar reads your install and puts the result on your clipboard. It sends nothing. It's there so you can paste it into a support thread yourself.
</Note>

## Uninstalling

Deleting the plugin removes **nothing** by default.

That's the opposite of most plugins, and it's on purpose. If you deactivate to test something, or delete and reinstall to fix a bad upload, you shouldn't lose a year of work to a routine action.

Each category has its own opt-in under **Settings → Data management**:

| Switch | Key | Removes |
| --- | --- | --- |
| Presets and their settings | `delete_links` | All four tables |
| Store settings, wording and licence | `delete_settings` | Every store setting (wording included), the stored licence record, each administrator's listing preferences, and cached preset data |
| The carrier product | `delete_carrier` | The hidden product, if it's still virtual and hidden |

<Warning>
  These fire on **delete**, not on deactivate, and they can't be undone. Turning one on does nothing straight away. It arms the deletion for whenever you next delete the plugin.
</Warning>

### What is never removed

Order line item meta stays, whatever you switch on. It's part of your order history, and an order that recorded which preset it came from should keep that record after the plugin is gone.

The carrier product is also left alone unless you opt in for it specifically. It's a WooCommerce product that may be attached to old orders, and deleting it would damage your order history.

## GDPR and data requests

The only personal data is the redemption record — a user ID or billing email against an order ID.

WordPress's own tools answer for it. **Tools → Export Personal Data** returns every preset an address claimed. **Tools → Erase Personal Data** anonymises those claims rather than deleting them, so a spent purchase limit stays spent. For the full detail, including why erasure keeps the row, see [Privacy and personal data](/cartpresets/settings/privacy).

## Moving to a new site

Presets are database rows, so a full database migration carries them.

If you're moving between separate stores, use [Import and export](/cartpresets/import-export)<Pro /> instead. It matches products by SKU on the way in, which a raw table copy can't do.
